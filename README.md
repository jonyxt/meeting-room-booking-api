# Meeting Room Booking API

[![CI](https://github.com/jonyxt/meeting-room-booking-api/actions/workflows/ci.yml/badge.svg)](https://github.com/jonyxt/meeting-room-booking-api/actions/workflows/ci.yml)

REST API для бронирования переговорных комнат. Сотрудники могут посмотреть свободные интервалы, забронировать комнату и отменить бронь. Администратор управляет пользователями и имеет доступ ко всем бронированиям.

Проект начался как тестовое задание. После его выполнения я переработал структуру приложения, добавил миграции, проверку прав доступа, тесты конкурентных операций и автоматические проверки в GitHub Actions.

## Что реализовано

- Регистрация сотрудников и вход по JWT.
- Две роли: `employee` и `admin`. Первый администратор создаётся отдельной CLI-командой, а не через публичную регистрацию.
- Просмотр комнат и свободных временных интервалов на выбранную дату.
- Создание бронирований с защитой от двойного резервирования одного слота.
- Отмена брони с сохранением истории: когда и кем она была отменена.
- Управление профилями и ролями с проверкой прав. Нельзя понизить в роли последнего администратора.
- Миграции PostgreSQL через Alembic и заполнение начальных данных.
- Проверки состояния приложения и подключения к БД (`/health/live`, `/health/ready`).
- Unit- и интеграционные тесты, Ruff и сборка Docker-образа в CI.

## Стек

**Python 3.13**, FastAPI, Pydantic, SQLAlchemy 2 (async), asyncpg, PostgreSQL 16, Alembic, PyJWT, bcrypt, pytest, pytest-asyncio, Poetry, Docker Compose, GitHub Actions, GHCR, Ruff.

Локальная разработка также ведётся на Python 3.14.

## Устройство приложения

Код разделён на три основных слоя:

```text
HTTP request
    |
    v
Router       — маршруты, входные данные, зависимости FastAPI
    |
    v
Service      — бизнес-правила, права доступа, транзакции
    |
    v
Repository   — запросы к PostgreSQL через SQLAlchemy
```

Основные каталоги и файлы:

```text
app/
  routers/           # HTTP-маршруты
  services/          # Бизнес-логика
  repositories/      # Работа с БД
  auth.py            # JWT, пароли, зависимости авторизации
  config.py          # Настройки из переменных окружения
  models.py          # ORM-модели
  schemas.py         # Pydantic-схемы
  bootstrap_admin.py # Создание первого администратора
  seed_data.py       # Начальные комнаты и интервалы
alembic/             # Миграции базы данных
tests/
  unit/              # Unit-тесты
  integration/       # Интеграционные HTTP-тесты
scripts/run_tests.py # Запуск тестового API и pytest
Dockerfile
docker-compose.yml       # Локальный запуск
docker-compose.test.yml  # Изолированное тестовое окружение
docker-compose.prod.yml  # Запуск опубликованного образа
.github/workflows/ci.yml
```

Доступность слота контролируется не только в коде: в PostgreSQL есть частичный уникальный индекс для активных бронирований одной комнаты на одну дату и один временной интервал. Благодаря этому параллельные запросы не могут создать две активные брони на один слот. При отмене используется блокировка строки `SELECT ... FOR UPDATE`. Для операций, связанных с сохранением хотя бы одного администратора, применяется транзакционная advisory-блокировка PostgreSQL.

## Быстрый старт

Понадобятся **Git** и **Docker с Docker Compose**. Устанавливать PostgreSQL и Poetry для этого варианта не нужно.

### 1. Клонировать проект

```powershell
git clone https://github.com/jonyxt/meeting-room-booking-api.git
cd meeting-room-booking-api
```

### 2. Создать `.env`

В PowerShell:

```powershell
Copy-Item .env.example .env
```

На Linux/macOS:

```bash
cp .env.example .env
```

В файле `.env` задайте свои значения `POSTGRES_PASSWORD` и `JWT_SECRET`. Для JWT нужен секрет длиной не менее 32 байт UTF-8. Остальные параметры шаблона подходят для локального запуска.

Пример генерации секрета, если Python установлен на компьютере:

```powershell
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

Не добавляйте `.env` в Git. В контейнерах адрес PostgreSQL задаётся через Compose; `POSTGRES_HOST=localhost` в шаблоне предназначен для запуска приложения непосредственно на компьютере.

### 3. Запустить приложение

```powershell
docker compose up -d --build --wait app
```

Compose последовательно запускает PostgreSQL, применяет миграции, создаёт начальные комнаты и интервалы, после чего запускает API. Тесты при старте приложения не выполняются.

Проверить состояние контейнеров:

```powershell
docker compose ps -a
```

После запуска доступны:

| Адрес | Для чего |
| --- | --- |
| http://127.0.0.1:8000/docs | Swagger UI |
| http://127.0.0.1:8000/openapi.json | OpenAPI-схема |
| http://127.0.0.1:8000/health/live | Проверка процесса API |
| http://127.0.0.1:8000/health/ready | Проверка API и PostgreSQL |

В пустой базе создаются три комнаты (большая, средняя, малая) и по три временных интервала для каждой: `09:00–12:00`, `13:00–16:00`, `16:00–19:00`. Повторный запуск заполнения не дублирует данные.

### 4. Создать администратора (при необходимости)

```powershell
docker compose exec app python -m app.bootstrap_admin
```

Команда запросит имя пользователя, email и пароль. Публичный `POST /register` создаёт только сотрудников. Повторное создание первого администратора через CLI заблокировано, если администратор уже существует.

### Остановить приложение

```powershell
docker compose down
```

Данные PostgreSQL хранятся в Docker volume и сохраняются после `down`. Команда `docker compose down -v` удалит также том базы данных.

## Как проверить API через Swagger

Swagger доступен по адресу http://127.0.0.1:8000/docs. Простой сценарий проверки:

1. Выполнить `POST /register` и создать сотрудника.
2. Отправить `POST /login` с `username` и `password`. Маршрут принимает **JSON**, а не форму OAuth2. Из ответа скопировать `access_token`.
3. Нажать **Authorize** в Swagger и ввести полученный токен для Bearer-авторизации.
4. Вызвать `GET /rooms`, затем `GET /rooms/available/{date}` с будущей датой.
5. Взять `room_id` и `time_window_id` из ответа и передать их в `POST /bookings` вместе с той же датой.
6. Проверить результат через `GET /bookings` и отменить бронь через `PATCH /bookings/cancel/{booking_id}`.

Пример тела запроса для создания бронирования:

```json
{
  "room_id": 1,
  "time_window_id": 1,
  "date": "2030-01-15"
}
```

ID здесь приведены для примера; реальные значения нужно взять из ответа API. Дата должна быть не раньше текущей.

### Основные маршруты

| Метод | Маршрут | Доступ |
| --- | --- | --- |
| `POST` | `/register` | Без авторизации |
| `POST` | `/login` | Без авторизации |
| `GET` | `/users/self` | Авторизованный пользователь |
| `GET` | `/users` | Администратор |
| `GET` | `/users/{user_id}` | Администратор |
| `PATCH` | `/users/{user_id}` | Свой профиль; администратор — любой профиль и роли |
| `GET` | `/rooms` | Авторизованный пользователь |
| `GET` | `/rooms/{room_id}` | Авторизованный пользователь |
| `GET` | `/rooms/available/{date}` | Авторизованный пользователь |
| `POST` | `/bookings` | Авторизованный пользователь |
| `GET` | `/bookings` | Собственные бронирования |
| `GET` | `/bookings/{booking_id}` | Собственная бронь; администратор — любая |
| `GET` | `/bookings/all` | Администратор, необязательный фильтр `date` |
| `PATCH` | `/bookings/cancel/{booking_id}` | Владелец брони или администратор |
| `GET` | `/health/live` | Без авторизации |
| `GET` | `/health/ready` | Без авторизации |

Описание схем запросов и ответов доступно в Swagger/OpenAPI. При ошибках используются стандартные HTTP-коды, в том числе `400`, `401`, `403`, `404`, `409` и `422`. Если база недоступна, `/health/ready` возвращает `503` без раскрытия деталей подключения.

## Тестирование и проверки

Интеграционные тесты отправляют HTTP-запросы к запущенному FastAPI и используют отдельную PostgreSQL. Для тестов выделен собственный Compose-файл; тестовая база не пересекается с локальной базой приложения.

Запуск полного набора:

```powershell
docker compose -p booking-tests -f docker-compose.test.yml up --build --abort-on-container-exit --exit-code-from tests tests
```

Очистка тестовых контейнеров и тестового тома:

```powershell
docker compose -p booking-tests -f docker-compose.test.yml down -v --remove-orphans
```

Скрипт `scripts/run_tests.py` применяет миграции в тестовой базе, запускает временный API, ожидает готовности `/health/ready`, выполняет pytest и завершает процесс API. Дополнительно предусмотрена защита от случайной очистки не той базы: сброс данных разрешён только для `test_db` с явно установленным `ALLOW_TEST_DB_RESET=1`.

На 30 октября 2026 года в CI успешно прошли **210 тестов**. Среди них — проверки прав доступа, валидации, отмены и конкурентного создания бронирований, а также операций с ролью администратора.

Ruff локально (если установлены зависимости Poetry):

```powershell
poetry run ruff check .
```

В GitHub Actions на `push` в `main` и в pull request запускаются Ruff и unit/integration-тесты. После успешных проверок при push в `main` собирается production-образ и публикуется в **GitHub Container Registry (GHCR)** с тегами по SHA коммита и `main`.

## Локальная разработка без контейнера для API

Для этого варианта нужны Python 3.13+, Poetry и запущенная PostgreSQL. Базу можно оставить в Docker:

```powershell
poetry install
docker compose up -d db
poetry run alembic upgrade head
poetry run python -m app.seed_data
poetry run uvicorn app.app:app --reload
```

Настройки подключения берутся из `.env`. В исходном шаблоне БД доступна на `localhost:3223`. Не запускайте одновременно локальный Uvicorn и контейнер `app` на одном порту.

## Что важно учитывать

- `docker-compose.yml` предназначен для локального использования. Порты API и PostgreSQL привязаны к `127.0.0.1`.
- `docker-compose.prod.yml` использует опубликованный образ из GHCR, но сам по себе не заменяет настройку защищённого публичного окружения (HTTPS, секреты, резервное копирование и т. д.). Публичное развёртывание в проект не входит.
- JWT содержит идентификатор пользователя, а актуальная роль проверяется по базе данных. Поэтому изменение роли влияет и на ранее выданные, ещё действующие токены.
- Отмена бронирования не удаляет запись: освобождённый интервал снова становится доступным для бронирования.
